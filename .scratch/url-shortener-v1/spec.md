# URL 단축 서비스 v1

## Problem Statement

긴 URL은 메신저, 문서, 발표 자료에 붙여 넣으면 읽기 어렵고 줄바꿈 때문에 깨지기도 한다. 사용자는 가입이나 로그인 같은 절차 없이, 긴 주소를 바로 짧은 주소로 바꿔서 공유하고 싶다. 짧은 주소는 입으로 불러 주거나 손으로 옮겨 적을 수 있을 만큼 단순해야 한다.

## Solution

웹 페이지에 Target URL을 붙여 넣고 제출하면 `https://도메인/42`처럼 숫자 Code로 된 Short Link를 받는다. 누구든 그 주소를 열면 Target URL로 이동한다. 로그인은 없고, 만든 Short Link는 영구히 유지된다. 같은 Target URL을 다시 제출하면 새 Code 대신 기존 Short Link를 돌려받는다.

## User Stories

### Short Link 만들기

1. 방문자로서, 로그인 없이 Target URL을 붙여 넣어 Short Link를 만들고 싶다. 가입 절차 없이 바로 쓸 수 있도록.
2. 방문자로서, 결과로 숫자 Code가 들어간 짧은 주소를 받고 싶다. 말로 불러 주거나 손으로 옮겨 적기 쉽도록.
3. 방문자로서, 결과 주소 옆의 복사 버튼으로 한 번에 클립보드에 복사하고 싶다. 직접 드래그해서 선택하지 않아도 되도록.
4. 방문자로서, 복사가 됐다는 표시를 보고 싶다. 붙여 넣기 전에 복사됐는지 확신할 수 있도록.
5. 방문자로서, 결과 화면에서 내가 넣은 Target URL을 함께 보고 싶다. 올바른 주소를 줄였는지 확인할 수 있도록.
6. 방문자로서, 이미 누군가 줄인 Target URL을 다시 제출하면 같은 Short Link를 받고 싶다. 같은 주소에 링크가 여러 개 흩어지지 않도록.
7. 방문자로서, scheme이나 host의 대소문자만 다르게 입력해도 같은 Short Link를 받고 싶다. 사소한 입력 차이로 중복 링크가 생기지 않도록.
8. 방문자로서, Target URL 앞뒤에 실수로 들어간 공백은 무시되었으면 한다. 복사 실수 때문에 오류가 나지 않도록.
9. 방문자로서, 경로나 쿼리가 다른 주소는 서로 다른 Short Link로 받고 싶다. 서버마다 다르게 해석할 수 있는 주소가 하나로 합쳐지지 않도록.
10. 방문자로서, 제출 중에는 버튼이 비활성화되었으면 한다. 두 번 눌러 요청이 중복되지 않도록.
11. 방문자로서, Enter 키로도 제출하고 싶다. 마우스를 쓰지 않고도 빠르게 줄일 수 있도록.
12. 방문자로서, 결과를 받은 뒤 바로 다른 URL을 이어서 줄이고 싶다. 페이지를 새로 고치지 않아도 되도록.

### 입력 오류

13. 방문자로서, `http`나 `https`가 아닌 주소를 넣으면 이유가 담긴 오류 메시지를 보고 싶다. 무엇을 고쳐야 하는지 알 수 있도록.
14. 방문자로서, 빈 값을 제출하면 오류 메시지를 보고 싶다. 아무 일도 안 일어난 것처럼 보이지 않도록.
15. 방문자로서, URL 형식이 아닌 글자를 넣으면 오류 메시지를 보고 싶다. 잘못된 링크가 만들어지지 않도록.
16. 방문자로서, 2048자를 넘는 주소를 넣으면 길이 초과 오류를 보고 싶다. 왜 거부됐는지 알 수 있도록.
17. 방문자로서, 이 서비스의 Short Link를 다시 줄이려 하면 오류 메시지를 보고 싶다. 링크가 자기 자신을 가리키는 루프가 생기지 않도록.
18. 방문자로서, 오류가 난 뒤에도 입력값이 그대로 남아 있었으면 한다. 처음부터 다시 입력하지 않고 고칠 수 있도록.

### 요청 제한

19. 방문자로서, 짧은 시간에 너무 많이 만들면 "잠시 후 다시 시도" 안내를 보고 싶다. 고장이 아니라 제한에 걸렸다는 걸 알 수 있도록.
20. 운영자로서, IP당 분당 10회를 넘는 링크 생성 요청을 거부하고 싶다. 봇이 Short Link를 무한히 만들어 DB를 채우지 못하도록.
21. 운영자로서, 리다이렉트에는 요청 제한을 걸지 않고 싶다. 링크가 많이 공유돼도 정상 방문자가 막히지 않도록.
22. 운영자로서, 요청 제한이 리버스 프록시 IP가 아니라 실제 방문자 IP를 기준으로 동작했으면 한다. 모든 방문자가 하나의 버킷을 공유하지 않도록.

### Short Link 따라가기

23. 링크를 받은 사람으로서, Short Link를 열면 곧바로 Target URL로 이동하고 싶다. 중간 페이지 없이 원래 목적지에 도착하도록.
24. 링크를 받은 사람으로서, 존재하지 않는 Code로 들어가면 "링크를 찾을 수 없음" 페이지를 보고 싶다. 빈 화면이나 서버 오류 대신 상황을 이해할 수 있도록.
25. 링크를 받은 사람으로서, `/007`처럼 앞자리에 0이 붙은 주소는 찾을 수 없음으로 처리되었으면 한다. 하나의 Short Link가 여러 주소로 접근되지 않도록.
26. 링크를 받은 사람으로서, 숫자가 아닌 경로에서는 단축 링크가 아닌 일반 페이지 동작을 보고 싶다. 서비스의 다른 페이지와 헷갈리지 않도록.
27. 링크를 받은 사람으로서, 몇 년 뒤에 열어도 Short Link가 동작했으면 한다. 문서에 박아 둔 링크가 깨지지 않도록.
28. 운영자로서, 리다이렉트가 302로 응답했으면 한다. 나중에 클릭 통계를 붙여도 재방문이 서버에 도달하도록(ADR 0003).

### 동시성과 일관성

29. 방문자로서, 다른 사람과 동시에 같은 Target URL을 제출해도 같은 Short Link를 받고 싶다. 동시 요청 때문에 중복 링크가 생기지 않도록.
30. 운영자로서, Code가 생성 순서대로 1부터 매겨졌으면 한다. 주소가 가능한 한 짧게 유지되도록(ADR 0001).
31. 운영자로서, 한 번 발급된 Code는 다른 Target URL을 가리키지 않았으면 한다. 공유된 링크의 목적지가 바뀌는 일이 없도록.

### 운영과 배포

32. 운영자로서, 서버 한 대에서 명령 하나로 앱, DB, HTTPS 프록시를 함께 띄우고 싶다. 배포가 단순하도록.
33. 운영자로서, HTTPS 인증서가 자동으로 발급되고 갱신되었으면 한다. 인증서 만료로 서비스가 멈추지 않도록.
34. 운영자로서, 앱을 다시 배포해도 Short Link 데이터가 유지되었으면 한다. 영구 링크라는 약속을 지킬 수 있도록.
35. 운영자로서, DB 스키마가 버전 관리되는 마이그레이션으로 적용되었으면 한다. 서버 DB가 코드와 어긋나지 않도록.
36. 개발자로서, 로컬에서 프론트 dev server와 백엔드를 따로 띄워 개발하고 싶다. 프론트를 고칠 때마다 이미지를 다시 빌드하지 않도록.
37. 개발자로서, 로컬에서도 운영과 같은 PostgreSQL을 쓰고 싶다. DB 차이로 생기는 버그를 운영에서 처음 만나지 않도록.

## Implementation Decisions

### 구성

- 저장소는 `backend/`와 `frontend/` 두 폴더로 나눈다.
- `backend/`는 Java 21, Spring Boot 4, Kotlin, Gradle(Kotlin DSL)로 만든다. 생성 API와 리다이렉트를 모두 맡고, 빌드된 프론트 정적 파일도 서빙한다.
- `frontend/`는 Vite, React, TypeScript로 만든 SPA다. 메인 페이지와 not-found 페이지 두 화면만 있다.
- 배포 산출물은 이미지 하나다. multi-stage Docker 빌드에서 프론트를 먼저 빌드하고, 그 결과를 Spring Boot의 정적 리소스에 포함해 jar를 만든다.
- 로컬 개발에서는 Vite dev server가 `/api/**`와 숫자 경로를 백엔드로 프록시한다.

### 모듈

- **Target URL 규칙**: 입력 문자열을 받아 정규화된 Target URL을 돌려주거나 거부 사유를 돌려주는 순수 함수다. Spring에 의존하지 않는다. 서비스 자신의 host는 설정값으로 주입한다.
  - 앞뒤 공백을 제거한다.
  - scheme은 `http`/`https`만 허용하고, host가 있어야 한다.
  - 정규화 후 길이는 2048자 이하여야 한다.
  - host가 서비스 자신의 host이면 거부한다.
  - scheme과 host만 소문자로 바꾸고, 경로, 쿼리, fragment, 끝 슬래시는 그대로 둔다.
- **Short Link 저장**: Code(identity로 발급하는 bigint 순번, 1부터 시작), 정규화된 Target URL(unique 제약), 생성 시각을 가진 테이블 하나를 둔다. 스키마는 Flyway 마이그레이션으로 만든다.
- **Short Link 생성**: Target URL을 정규화한 뒤 기존 Short Link를 찾고, 있으면 그대로, 없으면 새로 만들어 돌려준다. 동시 삽입으로 unique 제약 위반이 나면 기존 행을 다시 조회해 돌려준다. 호출자에게는 새로 만들었는지 여부도 알려 준다.
- **요청 제한**: Bucket4j 인메모리 버킷으로 IP당 분당 10회를 허용한다. 생성 API에만 적용한다. 클라이언트 IP는 Caddy가 넘겨주는 `X-Forwarded-For`에서 얻으며, Spring의 forwarded header 처리를 켜서 해석한다.

### API 계약

- `POST /api/links`: 요청 본문은 `{ "targetUrl": string }`이다.
  - 새로 만들면 `201 Created`, 이미 있으면 `200 OK`를 돌려준다.
  - 응답 본문은 `{ "code": number, "shortUrl": string, "targetUrl": string }`이다. `targetUrl`은 정규화된 값이다.
  - 검증 실패는 `400`, 요청 제한 초과는 `429`이다. 오류 본문은 `ProblemDetail`(RFC 9457)이며, 사람이 읽을 사유를 `detail`에 담는다.
- `GET /{code}`: 경로가 정규식 `[1-9][0-9]*`에 맞고 그 Code가 있으면 `302 Found`와 `Location: <Target URL>`로 응답한다.
  - 숫자 형태이지만 Code가 없거나, 앞자리가 0이거나, bigint 범위를 넘으면 not-found 페이지를 HTTP `404`로 응답한다.
  - 숫자가 아닌 경로는 이 라우트가 받지 않는다.
- `shortUrl`은 설정된 공개 base URL과 Code를 이어 붙여 만든다.

### 배포

- `docker compose` 하나로 Caddy, app, Postgres 세 서비스를 띄운다.
- Caddy는 Let's Encrypt 인증서를 자동 발급하고 app으로 프록시한다.
- Postgres 데이터는 named volume에 보관한다.
- v1 배포는 서버에서 `git pull` 후 `docker compose up -d --build`를 직접 실행하는 수동 방식이다.
- 공개 도메인과 DB 접속 정보는 환경변수로 주입한다.

## Testing Decisions

- 좋은 테스트는 외부에서 관찰할 수 있는 동작(HTTP 응답, 화면에 보이는 것)만 검증한다. repository나 service를 mock하는 계층별 테스트는 쓰지 않는다. 내부 구조를 바꿔도 테스트가 깨지지 않아야 한다.
- **백엔드 HTTP 경계(주 seam)**: 앱 전체를 띄우고 Testcontainers로 실제 PostgreSQL을 붙여 진짜 HTTP 요청을 보낸다. 상태 코드, 응답 본문, `Location` 헤더만 검증한다. 다음을 다룬다.
  - 생성(201)과 기존 링크 재사용(200)
  - 대소문자만 다른 Target URL의 재사용
  - 검증 실패마다 대표 사례 하나씩(400)
  - 302 리다이렉트, 없는 Code와 앞자리 0의 404
  - IP당 11번째 요청의 429와, 다른 IP는 영향받지 않음
  - 같은 Target URL 동시 제출 시 Short Link가 하나만 생김
- **Target URL 규칙**: 순수 함수 단위 테스트로 경계 사례를 빠짐없이 다룬다. scheme 종류, 대소문자, 공백, 2048자 경계, 서비스 자신의 host, 경로·쿼리·끝 슬래시 보존 등이다.
- **프론트 페이지 경계**: Vitest와 React Testing Library로 페이지 전체를 렌더링하고, 서버는 `fetch` 수준에서 대체한다(MSW 또는 fetch stub). 사용자처럼 입력, 제출, 복사를 수행하고 화면에 보이는 결과와 오류 메시지를 검증한다.
- 저장소에 아직 코드가 없어 참고할 기존 테스트는 없다. 이 spec의 테스트가 이후 테스트의 기준이 된다.
- E2E 브라우저 테스트는 v1에서 하지 않는다.

## Out of Scope

- 로그인, 계정, Short Link 소유권
- Short Link 수정, 삭제, 만료
- 클릭 수 등 통계
- 사용자 지정 Code(vanity URL)와 base62 같은 다른 Code 형식
- 방금 만든 링크 목록 같은 생성 기록 화면
- CAPTCHA, 악성 URL 검사
- 서버 여러 대로의 확장과 공유 요청 제한 저장소(Redis 등)
- CI/CD 자동 배포(git 원격 저장소를 만든 뒤 별도로 진행)
- E2E 테스트

## Further Notes

- 용어는 `GLOSSARY.md`를 따른다: Short Link, Code, Target URL.
- 관련 ADR: 0001(순번 10진수 Code와 재사용), 0002(계정 없음, 영구 보존, IP 요청 제한), 0003(302 리다이렉트).
- 특정 클라우드 업체에 묶이지 않는다. Docker가 설치된 Linux VM 한 대와 도메인 하나만 가정한다.
- Code를 차례로 열어 전체 Target URL을 볼 수 있다는 점은 ADR 0001에서 감수하기로 한 결과다.
